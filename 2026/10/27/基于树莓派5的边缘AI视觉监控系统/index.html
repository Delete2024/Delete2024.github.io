一、硬件介绍

树莓派：Raspberry Pi 5，搭配 Raspberry Pi OS (64-bit) 系统

摄像头：OV5647 传感器，是树莓派官方最早的 Camera Module v1，500万像素，通过CSI接口连接

二、系统设计

本项目先后尝试了三种不同的设计方案：

1、方案一

采用最简洁的设计：摄像头采集数据交给ai推理，ai推理完后把推理结果标注到图像上之后交给编码器，编码器对处理好的图像进行编码后交给视频流媒体，最后由视频流媒体进行分发。如图所示：

这种方案实现出来之后会有很严重的丢帧和卡顿，因为ai推理速度远远低于摄像头采集的速度，导致摄像头采集的很多帧都不能得到及时处理，只能丢弃。

最后没有采用这种方案。

2、方案二

这个方案基于方案一进行了优化，把最耗时的“ai推理”部分做成了一个独立的线程，不影响视频观看的流畅性，如图所示：

这个方案实现出来之后就很流畅了，摄像头采集到的数据如果ai线程来不及处理，就直接给编码器处理，最终视频流媒体拿到的数据是经过ai处理的图像和未经ai处理的图像两种混合在一起的。虽然不是每一帧都进行处理，但是帧率较高，肉眼看不出来。

这个方案勉强能用，但是ai推理部分需要完成：推理+标注。推理功能是无法避免的，但是标注功能是把ai推理的结果（若干个显示框）给画到图像上，这其中需要进行多次图像转换（因为摄像头输出的图像数据是NV12格式，但是画框用到的OpenCV库需要BGR格式的数据），这个操作非常耗时，完全可以挪给QT端来做。

因此，在这个方案上又进行了一次优化。

3、方案三

这个方案是把方案二的ai推理部分的标注工作给去掉了，改到QT端进行标注。ai推理部分只需要完成推理，推理结果存入独立的队列，再由一个单独的 TCP 服务线程将结果发送到 PC 端的 QT 界面，如图所示：

这个方案，稳定性和流畅度是三个方案里面最好的，最终的项目也是采用的这个方案。

4、视频流传输协议的演进

在确定了以方案三为“采集-推理-编码”的核心架构后，视频流分发协议的选型也经历了一次重要的迭代。

初代方案（HLS）：
项目初期，为了让 PC 端和浏览器能够直接观看画面，系统采用了 HLS (HTTP Live Streaming) 方案。由树莓派把编码器产生的视频流切割为 MPEG-TS 切片文件（.ts），并实时更新 .m3u8 播放列表，再通过 HTTP 服务器暴露给客户端拉取。

遇到的问题：
HLS 本质上是基于 HTTP 文件的“伪直播”。播放器必须等切片完全生成后才能拉取播放，导致端到端延迟高达 5~10 秒。此外，切片生成与拉取的节奏极易错位，导致画面频繁出现“转圈”卡顿，体验极差。

最终方案（RTSP + MediaMTX）：
为了彻底解决延迟与卡顿问题，项目引入轻量级流媒体服务器 MediaMTX，并将推流协议全面替换为 RTSP。树莓派直接将编码后的 H.264 裸流以 RTP 包的形式推送到 MediaMTX，消除了切片等待时间。最终在局域网内实现了 200ms 级别 的低延迟传输，画面丝滑流畅。同时，MediaMTX 强大的协议转换能力，也为后续分离式架构（QT 端拉流、浏览器 WebRTC 预览）提供了坚实的基础。

4、针对 Request 类补充

摄像头部分的主要功能是：采集图像数据供其他线程消费。这其中涉及一个很重要的内容：图像数据要怎么传递。从前面的代码可以看出，图像数据是通过 libcamera 库提供的一个类——Request——来进行传递的，所以这里对 Request 这个类做一些补充说明。

Request 可以理解为一张 “帧采集任务工单”：它把“往哪块内存写”（Buffer）、“这一帧怎么拍”（Controls）、“实际拍成什么样”（Metadata）以及任务状态打包在一起，交给相机执行，完成后通过回调交还给应用（即你的 requestComplete）。

4.1、核心结构

根据 libcamera 官方文档，Request 主要包含以下几类信息：

  • Buffer 映射（核心）：内部是 std::map<Stream*, FrameBuffer*>。用户通过 addBuffer() 绑定的是 FrameBuffer* 指针，Request 只引用、不拥有；同一个 Stream 只能绑一个 Buffer，重复绑定会返回 -EEXIST。FrameBuffer 的生命周期由 allocator 管理，调用者必须保证它在 Request 完成回调之前一直有效。
  • Controls（输入参数）：一个 ControlList。用户在 queueRequest 前设置它，告诉相机这一帧的期望参数（如曝光、增益），且只能放相机支持的 control，否则行为未定义。本项目未使用；若使用，注意 reuse() 会清空 controls()（只保留 buffer 映射），所以每次重投前都要重新设置。
  • Metadata（输出结果）：另一个 ControlList。帧完成后，硬件实际生效的参数会填在这里。它是只读输出，由相机侧写入。
  • 状态与标记：Status（Pending/Complete/Cancelled）、sequence（帧序号）、cookie（用户自定义标记，libcamera 不碰它，常用于在回调里找回自己的上下文）。

4.2、在本项目中，Request 的流转过程

  1. 初始化（绑定）：request->addBuffer(stream, buffer) 把一块 FrameBuffer 记在工单上。之后相机就知道把这一帧数据写到 buffer 指向的那块内存里。
  2. 投递：camera->queueRequest(request.get()) 把工单交给相机，此时状态为 RequestPending。
  3. 完成回调：相机拍完后触发 requestComplete(request)。回调里通过 request->status() 区分：RequestComplete（正常完成，可入队）或 RequestCancelled（停止时作废，直接忽略）。
  4. 复用（reuse）：request->reuse(Request::ReuseBuffers) 把状态重置回 Pending、清空 metadata，但保留之前绑定的 Buffer 映射（若用 reuse(0) 则会连映射也清掉，需重新 addBuffer）。这样无需重新绑定，直接 queueRequest 就能拍下一帧，避免反复创建对象的开销。本项目中，队列满（push 失败）时由 requestComplete 就地 reuse + queueRequest 重投；正常入队的帧则由处理线程消费完后负责 reuse + 重投，保证每个 Request 最终都回到相机，采集循环不断。
  5. 取消（Cancelled）：当 cameraStop 触发 camera->stop() 时，所有未完成的 Request 状态会被置为 RequestCancelled，且这些请求仍可能触发 requestCompleted 回调。所以回调开头用 if (request->status() == Request::RequestCancelled) return; 过滤，避免把作废的帧当成有效数据入队。

4.3、一个容易混淆的点

Request 只引用 FrameBuffer，不拥有它；FrameBuffer 归 allocator 管，Request 归 g_requests 管，两者生命周期独立。因此 cameraStop() 只释放 FrameBuffer（allocator->free(g_stream)，且必须先 camera->stop() 再 free，防 use-after-free），**不销毁任何 Request**；Request 在程序退出、全局 g_requests 析构时才销毁，销毁时也不会去 delete 那些 FrameBuffer。

4.4、总结

在这份代码里，Request 就是那个反复利用、在“相机采集”和“处理线程”之间流转的容器，它装着“内存地址的引用”和“帧的元信息”，而 reuse(ReuseBuffers) 是让这个容器能低成本循环工作的关键。

五、装配MediaMTX

配置好摄像头能采集图像之后，下一步按道理应该配置编码器，在本项目中，把编码和推流的功能给放一起了，都放在“编码器”这个功能模块里面。

根据前面的系统设计可以知道，推流走的是RTSP协议，因此需要一个RTSP服务器，MediaMTX在这里充当这个角色。因为推流必须有一个接收端，否则编码器在启动时会直接报错退出，所以推流之前要先配置好MediaMTX。

1、安装

MediaMTX安装方法如下：

启动后，MediaMTX会自动监听各个端口，本项目用到的端口有：

  • 8554（RTSP 协议端口）：树莓派编码好的视频流就是推送到这个端口。QT上位机也是从这个端口拉取视频流显示（QT端底层使用 FFmpeg 通过 RTSP 拉流，以获取更高的本地解码与渲染效率）。推流地址用的是：rtsp://127.0.0.1:8554/stream；拉流地址用的是：rtsp://192.168.2.187:8554/stream。
  • 8889（WebRTC 端口）：这个端口是给浏览器拉取视频流使用的。浏览器输入对应的地址就能直接看到画面，无需安装插件，在QT端写好之前，是用的浏览器进行调试。拉流地址是：http://192.168.2.187:8889/stream。

2、配置

安装好之后，默认情况下推流和拉流都是可以直接使用的，由于本项目后期需要录制 AI 训练素材，所以需要开启MediaMTX的自动分段录制功能。如果不需要开启视频录制功能，可以跳过本小节。

配置方法如下：

打开 mediamtx.yml 文件，在文件中找到 paths: 节点（在文件末尾），添加以下配置：

  • record: yes：只要的 C++ 程序推流到 stream 路径，MediaMTX 就会自动开始录制。
  • recordPath：录制文件的存放位置（存放路径里带时间戳）。
  • recordFormat: fmp4：录制成碎片化的 MP4 格式。
  • recordSegmentDuration: 10m：每 10 分钟切成一个视频文件。
  • recordDeleteAfter: 0s：设置为 0 表示不自动删除旧录像。

使用注意事项：

(1) 这个配置一旦开启，就会自动把视频流存成视频文件，请确保这项配置只在需要录制视频的时候打开，其他时候保持关闭（注释掉即可），防止占用空间过多。

(2) 录制视频时需要严格按照这个流程进行操作：

  • 配置并开启MediaMTX
  • 开启推流
  • 等待录制完成
  • 先关闭推流，确保视频文件正常结束
  • 关闭MediaMTX

六、编码器开发

本项目把编码+推流功能放在了一起，统称为“编码器”模块，因此“编码器”模块包含的主要功能是：把摄像头采集到的数据（NV12格式）先转换成编码器能接收的数据格式（YUV420P），然后进行编码（编码成H.264格式），然后把编码好的视频流发送到MediaMTX（通过RTSP协议）。

由于树莓派5不包含硬件编码器，因此编码工作采用软件编码的方式进行。

  • libswscale：图像缩放与色彩空间转换库，处理图像像素格式的转换。

3.4、补充

在”3.2、循环处理“这一小节中，代码片段”4.1、准备源数据给 sws“的部分有一个风险点，这里进行补充：

在将摄像头数据交给 libswscale 转换时，定义了 srcLinesize 数组来告诉 FFmpeg 每行图像数据在内存中的真实跨度（Stride）。

这里的潜在陷阱在于：NV12 格式中，Y 平面和 UV 平面在内存对齐要求下，它们的 Stride 可能并不相同。本项目的 srcLinesize 对 Y 和 UV 均使用了全局的 gYStride。因为在树莓派 5 上，640×480 的宽度恰好满足 PiSP 管线的 64 字节对齐要求，实际报告的 Y 和 UV 的 stride 刚好相等（都是 640），因此没有发生错位。

但如果以后在其他分辨率下运行（例如宽 720），硬件会在行末填充空字节以对齐，导致 stride != width。此时 Y 和 UV 的 stride 可能不再相同，不能继续用 gYStride 同时喂给两个平面。严谨的做法是：依据 libcamera 为当前流配置报告的 stride 值，分别设置 srcLinesize[0] 和 srcLinesize[1]，否则画面会出现颜色错乱或撕裂。
